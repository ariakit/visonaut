The document is fast. Then the run list waits for 6 D1 round trips in sequence and the alert count for 9 more, and each one crosses to another continent. The access rules of the contract need 4 of the 15. A Better Auth schema check takes 4 others, and one option turns it off.

The header links

The queue and the history are one route with one list, so a router link needs no request. The first sketch of this fix had 3 defects, and each one is measured:

  • Without exact, two header links get aria-current="page" on /?view=history.
  • Link throws without a router. 71 browser tests mount the workspace, with its header, without one.
  • A router navigation does not fire beforeunload. On the run page that prompt protects a decision that is still being sent, and line 196 of the contract says: “Unsent decisions still require the browser.” The run page needs useBlocker before its header and its Queue button can be router links.

Where the Worker runs

The Worker runs near the visitor, and D1 has no region in South America. One configuration key moves the Worker to the database.

The access check on each request

Line 186 of the contract sets the limits: “Private reads may reuse a positive GitHub permission result for the same valid session, user, and repository for at most 60 seconds. […] Live session and linked-account checks still run for every request.” Line 204 permits 10 seconds for Approve and Reject. The code keeps these limits, and pays more than they require:

  • The alert poll never uses the grant. The poll period and the lifetime are both 60 s, so each poll of each open tab calls GitHub.
  • A write check that succeeds deletes the grant and stores nothing. The first Approve of a visit makes 2 live GitHub checks in sequence.
  • A new isolate starts with nothing and makes 3 GitHub calls. How often a visit reaches a new isolate is not measured: Cloudflare gives “no guarantee that any two user requests will be routed to the same or a different instance” (Cloudflare: isolates).

Inside the contract, the lifetime cannot decrease the GitHub calls of the poll. Only the poll period can, and D-UX-05 in UI structure decides the refresh periods. The D1 reads are the larger cost. In a local D1 run, the access check made 5 round trips with the options of today and 2 with validateSchema: false and joins: true. Both are documented options (Better Auth: database).

Where the first data comes from

Today the request starts 199 to 303 ms after the first byte of the document. After the other fixes, the model has the same gap at 192 ms: 28 to 31% of the time to the list. Two ways close it. A script in the document head starts the same request sooner. A route loader on the server reads the list inside the document request. The second way is a new path to private data, and it must do by hand what the API path does today:

What a read in the document request must do
Rule Why
Return a promise, not the data A loader that awaits moves the server wait in front of the first byte: 0.9 to 2.0 s today, not 41 to 119 ms.
Leave the session renewal to a later request A streamed response sends its headers first, so the Set-Cookie of the renewal (one time each day) is lost. disableRefresh exists for this.
Do not render dates on the server runDate uses the locale and time zone of the machine, so the server text and the browser text differ: a hydration mismatch. ssr: "data-only" prevents it.
Check the origin The API rejects another origin. The document path has no such check, and production also answers on workers.dev.
Keep the response rules A server function answers without the security headers and without the 503 shape of the contract. A call to handleApi in the same process keeps both. The preview deployment has no database, so the read must return its sample data first.

For the streamed way, the router documentation says: “Deferred promises rendered with the <Await> component trigger suspense boundaries, allowing the server to stream html up to that point” (deferred data loading).

The run list between navigations

The review loop is queue, run, queue, and each return starts with the loading text. A route with a loader gets a cache from the router (1.170.38 is installed): “By default, staleTime is set to 0”, and “stale successful matches keep rendering with their existing loaderData while the loader revalidates in the background” (data loading). The cache does not survive a document load, so it needs the router links first. A staleTime of 15 to 30 s, as in the first sketches, shows a wrong row after an approval (2 verifiers).
