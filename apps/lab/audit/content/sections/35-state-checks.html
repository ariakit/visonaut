How a CI run proves that it may submit

Settled in revision r4: option 1, the OIDC token of GitHub Actions with no file check. This part is the research of revision r3 for decision D-OPS-04. Your note asked: I'm starting to think that this is a problem because we opted for authenticating through OIDC, is that right? Would it be simpler if we just used API keys? The short answers:

  1. Is OIDC the cause of the problem? No. The service does two separate things with each request of a CI run. The identity check learns who calls: GitHub signs an OIDC token for the job. The file check learns which code ran: the service reads ci.yml and app.yml and compares each file hash with a fixed value. The pin cutover and its failure window of 34 to 41 minutes come only from the file check. The OIDC token makes the file check possible, but it does not need it. The file check is 50 lines of the service: packages/security/src/oidc.ts:157-206.
  2. Would API keys be simpler? Simpler than today: yes. Simpler than the OIDC token with no file check: no. A key design has no pin cutover, but only because a key cannot say which code ran. You get the same result when you keep the OIDC token and remove the file check. That is option 1, your answer. For ariakit/ariakit the two designs are then almost equal: 3 permission lines and no secret, or 2 lines and 1 secret. For the service they are not equal. Option 1 deletes code. A key design adds a table, a settings page, and a new check of the run.
  3. Do most products use a key? Yes. All 6 CI products that revision r3 compared accept a key. 2 of them, Argos and Codecov, also accept the OIDC token of GitHub Actions. None checks a workflow file.
  4. A library or own code? Own code, if you add keys. One table and about 44 lines check a key with 1 D1 read and no write. The API key plugin of Better Auth writes 2 rows for each check, and your rule says that D1 writes that repeat must not increase. Unkey is a second system to run.
  5. Does a key help a pull request from a fork? No. GitHub gives a run that a fork starts no secret and no OIDC token. The two proofs are equal there.

What the file check protects, and what it does not

A capture job runs the code of the pull request and makes the screenshots. The Submit job runs no code of the pull request. It installs visonaut@0.5.4, compares each capture with the baseline, and sends the count of changed pixels. The service does not count pixels itself. It stores the number that the Submit job sends (apps/web/src/api/local-comparison.ts:529-571). The file check makes sure that a pull request cannot replace the Submit job, and that it cannot send the no-visual report for itself. The change that it stops is one line: 


    # .github/workflows/app.yml, line 259, in a pull request
    # before
    run: visonaut submit --shard linux --shard safari
    # after: a script of the pull request that sends "0 changed pixels" for each capture
    run: node scripts/submit.mjs

What the file check does not protect. A capture step runs pnpm -F app run test-visual, and that script is code of the pull request.   • Revoke. A button in the list sets revoked_at. 1 D1 write, by a person.
