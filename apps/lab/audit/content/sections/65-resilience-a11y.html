One decision, from key press to saved

The maintainer selected server storage for pending decisions, “with processing continuing after the window closes” (contract line 196). The same line says: “Admitted commands survive its closure, and failed commands remain visible through their receipts.” The server does both. After a reload, the page shows neither.

  • The only receipt read needs the command ID and the same reviewer. No request lists the receipts of a reviewer.
  • The server keeps each receipt until the run is archived. Processing starts in the request that stores the decision, and a scheduled job each 5 minutes does the same work. Thus the gap is a short time, or a fault of the processing.
  • That time is short on production. No lane measured it.
  • A queued decision that fails changes no verdict on the server. The harm is a decision that the reviewer must make again.
  • localStorage “persists even when the browser is closed and reopened”, for one origin in one browser profile.

Queue or direct save

Revision r2 asked this question, and in round 2 you kept the queue. The decision is settled, and each answer of the table below stays necessary. The question came from your answer “no promise” to D-RES-02: the page no longer says “You can close this window.” That sentence was the visible reason for the decision queue. You selected the queue on 2026-10-02 (contract line 196, pull request #190).

One example: you press A on one variant. The server has two paths for that request. The page uses the first one for each decision.

  1. The page sends POST /api/comparisons/<id>/commands with "queued": true. The server stores a task row.
    Answer: 202 with { "queued": true, "commandId": "…" }.
    D1 rows: 5.
  2. The server processes the task after the answer, in the same Worker call. If that fails, the operations queue processes the task later. The page gets no answer for this step.
    D1 rows: 22. 8 for the task row, and 14 for the decision.
  3. The page waits 500 ms and sends GET /api/commands/<command ID>/queued, then again each 500 ms.
    Answer: 202 while the task is not complete.
    D1 rows: 0.
  4. The page sends the same request when the task is complete.
    Answer: 200 with the result and the complete run model. For a decision that failed or lost a conflict: 409 with the run model and no reviewer field.
    D1 rows: 0.
  5. Later, when the run is summarized, the server deletes the task row. The page sends no request.
    D1 rows: 1 or more. They are not in the 27.
  1. The page sends the same POST /api/comparisons/<id>/commands without "queued". The server saves the decision in that request.
    Answer: 200 with the result: the new decision revision, the run revision, the run status, and your GitHub user ID. It has no run model when the revisions agree. For a conflict: 409 with the run model and the GitHub user ID of the reviewer who decided first.
    D1 rows: about 14. That is the 27 measured rows minus the 13 of the task row.
  2. No poll, no task row, and no row to delete later.
  • The page always sends queued: true (client.ts, line 317). So the direct branch of the server (review.ts, lines 879 to 904) has no caller. The page code reads its answer already: the poll loop runs only while the answer says queued.

A second agent ran the measurement again and got the same numbers. 13 is a lower limit: it leaves out the later delete and a retry.

What the queue gives, and a direct save gives up

  • A decision that the server stored survives a closed tab. The contract says: “Admitted commands survive its closure”.
  • The server processes fast decisions in their order.
  • The server tries a stored decision again by itself, 5 times at most. On the direct path the page must send it again, with the same command ID.
  • On the direct path the page sends one decision request at a time, so a fast second decision waits for the first answer.

What nobody measured

  • The time of one direct save in production. The request lasts as long as the save.
  • The time from HTTP 202 to the final receipt in production.
  • Several fast decisions on the direct path.
  • The rows that one direct save writes. The 14 is a subtraction.

The code has these two branches only, and nobody designed a third way. So the panel has two options, and none is recommended. You selected “Keep the queue”.

Why the page names nobody

  • The page sends each decision with queued: true (apps/web/src/review/client.ts, line 317). The answer for a queued decision that the service refused has the keys error and model only (apps/web/src/api/review.ts, lines 817 to 830).
  • The code has a second way to send a decision, with no queued. Its answer has a reviewer key. No page uses it. The client test gives that key the value “octocat”, so the test passes for a text that production cannot show.
  • The reviewer value is the GitHub user ID. A decision stores only that number, in the column actor_id. No table has a column for the login (the GitHub user name, for example morikenji).

Thus two parts are missing. The page does not read the reviewer from the run model that it gets. And the run model has a number where a person needs a name.

How often a conflict can happen

  • 10 people can sign in. The GitHub App that Visonaut uses for sign-in is private, and GitHub lets only the members of the organization that owns a private App sign in with it. The ariakit organization has 10 members. Nobody tested a sign-in with an account from outside.
  • 4 people can review. 5 of the 10 accounts have write access or more to ariakit/ariakit: 2 with the admin role and 3 with the write role. 1 of the 5 is the automation account. The other 5 have the triage role: they can sign in, and the service refuses their requests.
  • One person makes almost all merges. From 2026-09-06 to 2026-10-06, 232 pull requests were merged into ariakit/ariakit: 159 by one person, 72 by the Renovate bot, and 1 by a second person. This is a count of merges on GitHub. It is not a count of review decisions in Visonaut, which nobody counted.
  • One person alone can also get this conflict. Two tabs: tab 1 approved a variant, tab 2 still showed “Needs review”, and the rejection from tab 2 got the same 409. The same happens after a reload while a decision is queued.
  • The repository records one conflict on a deployed service, in docs/evidence/deployed-review, from 2026-09-22: “Updated by 3068563.” Both review sessions of that test had the same GitHub identity. Its report says that it does not prove the behavior between two people. The page queues each decision since pull request #190 of 2026-10-02, and a queued decision cannot give that text.
  • Nobody counted the conflicts in production. The audit had no read access to the production database. Two read-only statements give the numbers: the count of different actor_id values of the human decisions, and the count of queue rows of the kind review whose result starts with “A target changed”.

Thus the conflict that occurs first is your own second tab, or your own reload. A conflict between two people is rare while one person makes almost all decisions. It becomes normal when a second person reviews. Each option must give a good text for both cases.

      // The page finds the variant that changed, and the decision that it has now.
      function conflictingDecision(command: ReviewCommand, model: ReviewModel) {
        const expected = new Map<string, number>();
        for (const target of command.targets) {
          expected.set(target.id, target.expectedRevision);
        }
        for (const item of model.items) {
          for (const variant of item.variants) {
            const revision = expected.get(variant.id);
            if (revision === undefined) continue;
            if (variant.revision === revision) continue;
            // An Undo or an automatic decision: no person to name.
            if (variant.source !== "human") return null;
            if (!variant.verdict) return null;
            if (!variant.reviewer) return null;
            return { verdict: variant.verdict, reviewer: variant.reviewer };
          }
        }
        // Another kind of conflict: no variant of the decision changed.
        return null;
      }

      // The page builds the text. `serverMessage` is the text of today.
      function conflictText(command: ReviewCommand, model: ReviewModel, serverMessage: string) {
        const decision = conflictingDecision(command, model);
        if (!decision) {
          return `Conflict. ${serverMessage}`;
        }
        const lost = command.verdict === "approved" ? "approval" : "rejection";
        if (decision.reviewer === model.viewer) {
          return `Conflict. You already ${decision.verdict} this variant. Your ${lost} was not saved.`;
        }
        // The option with no name always says "Another reviewer".
        const name = Object.hasOwn(model.reviewers, decision.reviewer)
          ? model.reviewers[decision.reviewer]
          : "Another reviewer";
        return `Conflict. ${name} ${decision.verdict} this variant. Your ${lost} was not saved.`;
      }
