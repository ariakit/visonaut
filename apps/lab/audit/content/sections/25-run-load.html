Why a run page is slow

A run page shows one loading sentence for 6.7 to 7.8 s. The server uses 5.3 to 5.7 s of it to download two inventories from R2 and validate them again, so that one response can list 3,832 variants. In the three measured runs, no variant needed a review.

Where the server wait goes

The sum does not close. 10 round trips in sequence, with the schema check, are 1.3 to 1.5 s. The request needs 0.60 to 0.70 s of CPU on a laptop, in local workerd, and production renders the sign-in document 2.2 to 3.3 times slower than that laptop. With that factor, the CPU part is 1.3 to 2.3 s, and 1.5 to 3.1 s are left for 24.3 MB from R2 and for up to 3 GitHub calls (0 to 1.0 s). Nobody measured that part, and each part has another fix.

One trace divides it, with no code change: the configuration enables traces. A trace has the CPU time of the request (cloudflare.cpu_time_ms), one r2_get entry for each read, and one fetch entry for each GitHub call (reference). Cloudflare keeps a trace for 7 days and calls the feature an early beta. If production stores them, the traces of the three measured requests stay until about 2026-10-12.

In this model, the no-regret lists of the two load sections remove 0.5 s. A complete model with a faster read shows the workspace at 4.2 to 4.5 s. Only the attention-first response brings it below 2 s. Limit: the 1.4 s of browser time comes from a hidden tab.

One image request

Each first view of an image is 1 Worker request with 1 D1 read and 1 R2 read. The same path with no R2 read answers in about 0.15 s from São Paulo (146 to 175 ms in four runs). A request with no D1 read answers in about 0.03 s. Nobody measured a real first view: the R2 read and the transfer (median 11.9 KB for a card image) come on top. Requests run in parallel, and a repeat view comes from the browser cache in about 1 ms.

This is the price of the mask at load that you selected in D-WORK-02, in the viewer section: one more request of this kind for each changed variant, and a decision that waits for 3 images in place of 2. The preload of the list then needs the mask too.

An edge cache for images is not in the list. The Cache API "is local to a data center", so the first view of a reviewer is a miss, and the browser keeps each image for one year already. Workers Cache shares one copy between data centers, but each deploy starts it empty by default, and a copy stays after the service deletes the image bytes unless the deletion purges it: a retention choice for a small gain.

The first response lists each variant

With only the rows that D1 stores, the same request returns 7,483 bytes, makes no R2 read, and needs 0.3 ms of CPU where the complete model needs 870 ms (Node, laptop). In production that is 3.9 to 4.5 s less server wait. The 4 changed variants of the fixture are test data: the three production runs had none.

That response is not complete today. It has no baseline image: Submit writes NULL for the baseline capture of a changed row. A removed capture has its name only in the inventory of the baseline. So an attention-first response needs one new D1 column that Submit fills.

The contract has two lines about this: line 26 ("Review reads the full inventory to show unchanged items") and line 148 (P01, "One compact complete model"). The record of P01 says: "A new page/detail protocol should have a measured reason." The router can draw the first response while a second one loads (deferred data).

Each read validates two inventories again

One review read checks the size and the digest of each object and then validates it as new data. The digest check is 9 ms. The other checks are the cost.

A /pulls link pays for the access check two times

The pull request page is not in front of each review. A new check has a /pulls link, and the first status delivery replaces it with /runs/<id> (GitHub lets an app update the link of a check). So the page is a waiting room. On the other paths, the lookup adds 0.99 to 1.23 s (second control of the example above). Nobody measured how often a reviewer takes those paths.

Each decision pays for the page load again

The next variant shows at once, so this wait blocks only the text "Saved" and Undo. A ready decision receipt builds the same model as the page load, so its server wait is probably the same 5.3 to 5.7 s. Nobody measured a save in production.

The stored decision receipt has the field previousRunRevision already, and the page can apply an answer with no model. In a test of the audit, the page model after that step was equal to a new server model for an approval, a rejection, and a chain of four approvals. Undo is another case: its result has no restored verdict, so it keeps the model.

Model reads that overlap share one isolate. In local workerd, 3 at the same time need 3.1 times the time of one, and one read holds 45 MiB of live heap at its largest point. With their read buffers, 4 reads are 130 MiB against a limit of 128 MB (third slider of the calculator above). Nobody proved that the buffers count. A fast review of 5 or more changes can make 4. Above the limit, Cloudflare "lets in-flight requests complete and creates a new isolate", so no decision is lost.
