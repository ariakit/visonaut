How a decision is saved today

One decision is one command. The page sends it, the Worker stores it as a task, and the review service applies it in one D1 batch. A batch is one transaction: "If a statement in the sequence fails, then an error is returned for that specific statement, and it aborts or rolls back the entire sequence" (Cloudflare, batch()). The rule "every target or none" of the review guide is that transaction.

    INSERT INTO visonaut_assertions (valid) SELECT 0 WHERE CASE WHEN (EXISTS (
      SELECT 1 FROM visonaut_comparison_rows

Four designs for the approval of a whole run

Your rule is that D1 writes that repeat must not increase. The reference is the product of today: the reviewer approves the run one screenshot at a time. The check passes only when each change has an approval, so the reviewer writes these approvals in any case. A design that writes more rows than that reference is out. No design does. A run approval that D1 refuses

The issue plan asked one more question: what does the server do when a run approval is too large for one D1 transaction? This is not a new decision. Two of your answers and one rule of D1 close it.

  • D-WORK-04: the server writes the approval "in one transaction". A D1 batch is that transaction: "If a statement in the sequence fails, then an error is returned for that specific statement, and it aborts or rolls back the entire sequence" (Cloudflare, batch()). So a refused run approval saves nothing. No design is necessary for that.
  • D-SCALE-02: for a run with more changes than one transaction can hold, your answer is a stated limit of changed captures, and nothing is built for it now. An approval in parts is the option of that decision that you did not select. A menu item that is off above some count is that limit in a small form, and its number needs the measurement on production D1 that waits with the limit. The run approval is also not the largest transaction: the closed summary of today writes 8 rows for each change, where the run approval writes 5 (local D1). It runs 30 days after a run closed, with no action of a person. So a guard for the menu item alone does not answer a mass change, and the one limit answers both.
