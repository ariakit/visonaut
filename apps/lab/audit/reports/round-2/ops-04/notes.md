## 1. The user problem

The maintainer wrote: "I don't understand this. I need a better explanation with concrete examples. I want what is simpler to the consumer."

"Consumer" means the people who edit `.github/workflows` in `ariakit/ariakit`. Their problem today: each edit of `ci.yml` or `app.yml`, also in a job that has nothing to do with screenshots, needs a change in a second repository, a deployment, a repository variable change, and a merge in a hurry. It also makes the runs of other pull requests fail.

### 2.3 What the pins protect, and what they do not

- **Protect.** A pull request cannot change the Submit job (the judge that counts changed pixels) or the Plan job (which can say "no captures needed"). Refusals measured in experiment 2: `rest.direct_workflow_blob` and `rest.caller_workflow_blob`, both 403 `untrusted_run`.
- **Do not protect.** The capture job runs pull request code. From the audit (`reports/gap-trust-boundary/report.md:86-97`): loose `comparison` settings (measured, TRUST-03), images equal to the reference bytes (code reading), new identities, and omitted identities (TRUST-04) all pass the CLI and the service today. The earlier decision A02 says the same: "Candidate capture code can already supply false pixels; do not claim screenshot truth" (`docs/simplification-audit/audit-data.json`, entry A02, `risks`).
- **What follows for options 1 and 2.** An honest Submit job does not make the check safe against an account with push access. It keeps the numbers and the settings true for the images that were submitted. The answer D-AUTH-04 = `show-settings` of round 1 uses the manifest that the Submit job sends. It is true in each honest run in each option. It can be false only when a pull request replaced the Submit job (option 1), and such an author can also write images that are equal to the baseline.
- A blob pin does not fix the code behind an action tag (TRUST-07).
- Attackers: only accounts with push access to a branch of `ariakit/ariakit` (`oidc.ts:300` refuses another head repository).

### Experiment 1: does a workflow edit always ask for captures?

- Question: does the planner that the Plan job runs today (Ariakit commit `c87988ef`) set `app=true` when a pull request changes only a workflow file? This decides if "accept the no-visual report only when `ci.yml` equals the file on main" would ever refuse an honest pull request.
- Expected: `app=true` for each path below `.github/`, `app=false` for a text file.
- Script: `scripts/probe-planner.mjs`. It imports `createCIPlan` from a copy of `packages/ariakit-scripts/src/ci.ts` at `c87988ef`.
- Observed (first agent, and the checker again): `.github/workflows/ci.yml` → true; `.github/workflows/app.yml` → true; `.github/workflows/setup/action.yml` → true; `packages/ariakit-scripts/src/ci.ts` → true; `contributing.md` → false; `app/src/examples/combobox/index.tsx` → true. As expected. Real case that agrees: #7708 changed `ci.yml` and `contributing.md`, and its job `App / Visual Submit` ran (check run list of commit `e3a65a6d`).
- Limit: this is a rule of consumer code. If Ariakit removes it, a pull request that edits `ci.yml` and needs no captures would fail its Plan job under option 2 or 3.

### Option 2 in more detail (a proposal, nothing is built)

- Service repository: `.github/workflows/submit.yml` with `on: workflow_call`. One job: set up Node, `npm exec --yes --ignore-scripts --package=visonaut@<version> -- visonaut submit --shard linux --shard safari` (the form of `ci.yml:70`), upload the receipt. It checks out no consumer code and uses no cache that a pull request can write. It sets `VISONAUT_SERVER` and the job names itself, because the workflow-level `env` of the caller does not reach it. Permissions: `actions: read`, `contents: read`, `id-token: write`, given by the consumer job.
- Service check: `claims.job_workflow_ref === "ariakit/visonaut/.github/workflows/submit.yml@refs/heads/main"`. The other checks stay: repository ids, `workflow_ref` = `ci.yml` of the consumer, run, attempt, job name, pull request. The job name becomes `App / Visual Submit / <job name in the service file>`. The service can store `job_workflow_sha` with the run as a record; it does not compare it.
- Which ref: the branch `main` needs no new rule (the branch has a rule set) and no extra step. A change of `submit.yml` is then live for new runs about 4 to 5 minutes before the deployment of the same commit ends (deploy time 3 min 53 s to 4 min 49 s, from the audit). A tag such as `v1` lets the service maintainer move the judge after the deployment, but it needs a new tag rule (0 tags and no tag rule exist) and one more manual step for each change. The checker changed the example from the tag to the branch, because the simpler design wins. The draft preferred the tag.
- No-visual report: stays a step of the Plan job. Trust rule: the blob of `ci.yml` at the tested commit equals the blob of `ci.yml` at the target commit (`parents[0]`, which the code already has at `oidc.ts:319`). One more GitHub read on that path for a pull request (estimate from code), none for a push. No stored value. A run that started before a merged `ci.yml` edit still passes, because its tested commit has the old target commit.
- Removed from the service: `trustedWorkflowPath`, `callerWorkflowBlobSha`, `reusableWorkflowSha`, the 2 content reads, the comparisons in the 7 files (the stored columns stay and hold the claim value), the runbook `adapter-service-pins.md`, the caller census. The proof "the Plan job selected app=true" (`pre-run-plan.ts:84-163`) rests on the pinned `ci.yml` today; with no pin it shows only that a job with the name Plan passed.
- Removed from the consumer: lines 224-267 of `app.yml` (replaced by 8 lines), the variable `VISONAUT_WORKFLOW_SOURCE_SHA`, the fixed checkout `c87988ef` of the Submit job, the CLI version line of the Submit job. `ci.yml:70` keeps one CLI version for the no-visual report.
- D1 writes: no new write. The staged run row already stores a workflow ref and a source digest. GitHub requests: 2 fewer for each Submit verification (measured in the probe), 1 more for a no-visual report of a pull request (estimate).
- `VISONAUT_PACKAGE_SHA256`: the Submit job compares it with the manifest today (`bundles.ts:49-55`), and the server compares the manifest with `VISONAUT_TRUSTED_EXECUTOR_DIGEST`. PIPE-05: it is a declared text, not a measured hash. In option 2 the value moves to the service file, or the comparison goes away. While the service compares it, each release of the capture package stays a change in two repositories with an order. That is true for each option of this decision.
- List of shards (earlier decision D39): with `--shard linux --shard safari` in the service file, a pull request cannot leave out one of the two capture jobs: the CLI needs both artifacts. To add a shard, the service file changes first. The other choice is an input of the call; then a pull request can shorten the list, which has the same effect as omitted identities from capture code (TRUST-04).
- Renovate: one rule, `{ "matchDepTypes": ["workflow"], "pinDigests": false }` (documented). Without it, Renovate opens a pull request that replaces `@main` with a commit, the claim then holds the commit, and the Submit of that pull request is refused. That failure is closed: the pull request cannot merge.
- TRUST-07 (archive hash check of the CLI, commit pins for the actions of the Submit job): in option 2 these are changes of the service file only.

## 5. Recommendation and what would make it wrong

Recommend `service-workflow`.

1. By the maintainer's rule (simpler for the consumer), options 3 to 6 lose: each keeps a pin cutover or an admin bypass for a workflow edit or a Renovate action update.
2. Options 1 and 2 are equal for each later edit: the consumer does nothing.
3. Option 2 leaves less in the consumer repository (8 lines in place of 44, no CLI version in `app.yml`, no variable).
4. Option 2 keeps the guarantee that the contract states (lines 218 to 230) in a form that costs the consumer nothing: a pull request cannot replace the program that counts. The maintainer selected the pin model over `identity-only` in A02. Removing the guarantee is a policy choice that the maintainer must make, so the recommendation does not make it.
5. The mechanism ran in production on 2026-09-24 (upload path), the verifier code for it still exists and behaved as expected in the probe, and public data shows the claim value for a nested call.
6. No D1 write is added, and 2 GitHub reads go away for each Submit.

What the checker tried against it, and the result:

- **"Option 1 is simpler and gives up nothing real."** Partly true, and the text now says so. An account with push access can already make false screenshots in the capture code (4 ways, 1 measured), so the honest judge is not a complete protection. The difference that stays: 5 accounts can push to `ariakit/ariakit`, 2 to `ariakit/visonaut`; in option 2 the counting program is outside the pull request; and the consumer keeps fewer lines. Option 1 is less to build (it only deletes). The recommendation survives as the default, and option 1 is named as the right choice if the maintainer trusts each account with push access for the count too.
- **A hidden D1 write.** None found. The "same as main" rule is two content reads in the request. The stored run row keeps its columns.
- **A limit that stays.** The package digest comparison (2.1, PIPE-05) keeps a two-repository order for each release of the capture package in each option. The section and the decision name it.
- **A rule of the contract that it breaks.** Lines 218 to 230 change, and the answers A02 and D39 change. The section and the decision say so.
- **A simpler option that was not considered.** An action in the service repository (rejected: no claim names an action). A Submit workflow that runs from `main` through `workflow_run` (rejected, section 6).

It is wrong if:

- The maintainer trusts each account with push access to `ariakit/ariakit` for the count too. Then `no-file-check` is less to build and equal for each later edit.
- The maintainer wants the service maintainer to review each change of the capture steps and of the other CI jobs. Then `small-workflow` or `keep-two-files` fits.
- A run in `ariakit/ariakit` shows a claim value other than `ariakit/visonaut/.github/workflows/submit.yml@refs/heads/main`, and a direct call from `ci.yml` is not acceptable.
- The two files stay as they are (0 edits from 2026-10-03 to 2026-10-06). Then the pins cost nothing, and the refactor costs one CLI release and one last cutover.
