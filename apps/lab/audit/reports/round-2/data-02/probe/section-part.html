The run inventory and its limit

Your note on D-DATA-02 asked for a simpler way. It said that about 10 MB and a limit of about 6,000 captures is not acceptable, that D1 writes must not increase, and that backward compatibility is not necessary. This part answers the note with new measurements and new options. The short answer has two parts.

  • Yes, there is a simpler form. The file says each fact 2 to 6 times. With each fact stored one time, the same inventory is 1.58 MB in place of 12.15 MB, and no fact is lost. The 16 MiB limit then holds 40,000 captures. No D1 statement changes.
  • But the stop at about 6,000 captures is not in the inventory. CLI 0.5.4 refuses a manifest file above 8 MiB, which is about 5,700 captures. No inventory format moves that stop. Only a new CLI version in the workflow files of Ariakit does.

What the inventory is

The run inventory is one JSON file in R2 for each run. It is the complete list of the captures of the run. For each capture it has the name, the variant, the browser settings, the image that the service keeps, and the result of the comparison with the baseline. It also holds the manifest, which is the list of captures that the Submit job sends.

D1 holds only a pointer to the file: its key, its digest, its size, and the capture count. D1 also holds one row for each changed capture. Pull request #247 selected this split to keep D1 writes low. Its probe counted 66 rows written for a run of 100 unchanged captures, against 1,866 with one row for each capture. Each option below keeps this split.

The prototype turned the complete inventory into rows and back. The result had the same canonical JSON as the original, and the manifest had the same digest. So the rows are another way to write the same facts. They are not a summary.

Why the file has a limit today

The limit is one constant, maximumCaptureInventoryBytes, and the write throws above it. Its comment gives the reason: "Leave room for the decoded JSON and capture graph in a 128 MiB Worker." So it protects the memory of one isolate, which is 128 MB. A reader holds the text of the file and the objects that it parses from the text.

  • It is not a limit of R2. One object can have 5 TiB.
  • It is not a limit of a queue message or of D1. Both carry the pointer only.
  • It is a choice, not a measured bound. Pull request #247 calls it "document-size and behavior evidence, not a measured Worker heap limit".

The limit already stopped production one time. On 2026-10-04 the first Ariakit submission had an inventory of 18.8 MB. Pull request #249 then removed the capture details that the embedded manifest can give back, which made the file 12.2 MB. With the real writer, 5,250 captures are stored at 99.6% and 5,326 captures throw. When the write throws, materialization tries each hour for 24 hours. The GitHub check gets no final state, and each such run keeps one of the 5 places for active runs.

What the rows cost

  • Not less code in that file. The prototype has about 520 lines for the two directions. It replaces about 200 lines: the second packed form of pull request #249 and the checks that compare the two copies. What gets simpler is the data: each fact is in one place.
  • Stored inventories. The new reader does not read the form of today. The baseline, and each older baseline that an open pull request can still use, needs one conversion: one R2 write and one pointer update for each, one time. Older runs lose their capture list, unless the script converts them too. A new run writes the same D1 rows as today.
  • Reverse. A revert of the code is not enough after runs use the rows. The same conversion runs in the other direction, or the baseline is imported again.
  • Not measured. Time and memory in a Worker, the transfer time from R2, and the CLI part of the third option. In that option the digest of the manifest must be the digest of the rows, so that the Worker never builds the long form of today: 73.7 MB of text at 40,000 captures. The imported baseline has no manifest: the prototype keeps its facts, but its rows are not short.
