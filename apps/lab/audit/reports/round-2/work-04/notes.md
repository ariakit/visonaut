### What a run approval needs from the four rules

All four. The proposal for each is in the table "Rules for a review decision that is larger than one screenshot" of the section.

1. Images on screen: no image. The current state of the run on the page, and the confirmation names the changes that were not opened.
2. Frozen targets: the changes with no decision at the run revision of the confirmation. The request carries the run revision and the count.
3. Undo: one Undo sets each target back to "needs review" and restores the selection. Refused when a target changed, as today.
4. One refused target: every target or none. With rule 2 this is one guard on the run revision.

The fifth rule of the option "approve all seen" (what "seen" means) is not necessary as a gate. The count of opened changes in the confirmation is information only.

### Recommendation and what makes it wrong

Recommended: `approve-run` (decision rows). Reasons: it is what the note asks for, it writes fewer rows than the same approvals today (measured on local D1), it needs 18 statements for any run, and it changes no reader of decisions. `approve-run-one-row` writes 19,160 rows fewer for the largest run, which is 2 US cents at the documented price, and it puts a second meaning of "approved" in 11 source files.

It is wrong if: (1) production D1 refuses or bills the two set statements in another way than local D1 (not measured), (2) the maintainer wants the fewest writes more than one meaning of "approved", (3) run approvals become frequent, so that the 5 rows for each target matter, or (4) the maintainer wants the protection of D02 back, which points to `keep-scope` or `seen-set`.

### How I tried to refute the recommendation "approve-run"

- A hidden D1 write. None found. One command writes 1 row to the status outbox where 41 commands write 41, so the later status delivery also writes less. The rows that a run copies to closed history are one for each decision row in both cases. Undo writes 3 rows for each target and 9 for each command in both cases.
- The standing rule "no increase of D1 writes". It holds for each run design, because the check passes only when each change has an approval (`review-status.ts:34-35`, `:92`): the reviewer writes the 246 decision rows in any case. The run approval removes 40 × 21 rows.
- A limit that stays. The two statements have 5 and 3 bound values (limit 100) and a fixed length. Statements of the same form run for each comparison today (`local-comparison.ts:612-626`, with the comment "Set-based statements keep a 10,580-image run bounded in request size"). Not measured on production.
- A simpler option. Design 2 (one list, no server change) is simpler in code. It is out by the documented row limit of 2,000,000 bytes at about 3,690 targets, and one Ariakit run has 3,832 variants. The statement limit alone would not put it out: nobody knows how a batch counts, and the Worker sets 250,000 subrequests.
- A contract rule. The contract says that a variant action needs its evidence ready, and that a whole screenshot "need not open every variant, but the displayed current item/comparison must be ready and command targets must be frozen" (`docs/simplification-audit/contract-issue-1.md:266`). The run approval needs new text there. The section proposes it (4 rules).
- The definition of "no decision". The prototype uses `decision_id IS NULL AND source_decision_id IS NULL`. The page uses "no decision in force". I searched each writer of `visonaut_decisions` and of `decision_id` (`review-commands.ts`, `local-comparison.ts`, `rendering-profile-conversion.ts:77`, `history.ts:173`) and found no path that leaves a row with a pointer to a decision that does not count. If one exists, the count guard refuses the run approval. It does not approve a wrong variant.

The recommendation stays. What would make it wrong is in the final answer of this lane.
