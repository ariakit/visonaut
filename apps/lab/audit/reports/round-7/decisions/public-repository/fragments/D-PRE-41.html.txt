<h3 id="access-public-issues">What the public repository says about these findings, and when</h3>

<p>
  <strong>New question of 2026-10-07.</strong>
  <span data-fact="measured"
    >The repository ariakit/visonaut is public, so each person on the internet can read each issue,
    each pull request, and each pushed branch.</span
  >
  Two of your answers of that day publish audit text. You said: "You can file the issues yourself."
  And the lab goes to a branch, and the folder <code>apps/lab/audit</code> of the lab holds this
  record and its reports. This part answers one question: which findings must not be in public text
  with their steps before the fix is in production.
</p>

<p>
  <span data-fact="counted"
    >Of the 568 findings, 48 describe a way to get around a review rule, to get a token, or to slow
    or stop the service.</span
  >
  <span data-fact="counted"
    >For 38 of the 48 the weak place is in the public code, and for the other 10 a part of it
    is.</span
  >
  So no finding is a secret. The question is how much work a public text saves an attacker. The
  actors are the ones of <a href="#access-who">Who can do what</a>.
</p>

<ul class="wide">
  <li data-fact="counted">
    <strong>How bad the 7 are.</strong> The record rates 2 of the 7 findings of the first two groups
    as medium (AUTH-09 and AUTH-16) and 5 as low. It found no way from a caller with no credential
    to private review data, to a decision, or to the baseline.
  </li>
  <li data-fact="counted">
    <strong>Where the weak place is.</strong> For the first group it is in two tracked files:
    <code>apps/web/src/server.ts</code>, lines 82 to 87, has no path filter, and
    <code>packages/security/src/auth.ts</code>, lines 21 to 79, turns no route of the library off.
    For the second group it is the order of <code>apps/web/src/api/index.ts</code>: lines 123 to 126
    read the project from the database, and line 130 builds the sign-in library, before the
    credential check of line 194.
  </li>
  <li data-fact="counted">
    <strong>What is public today.</strong> No tracked file of the repository names the route that
    returns a token (<code>git grep</code> for the route names: 0 files). Below
    <code>apps/lab</code>, 10 files name it and 21 files name the 7 findings. Each of them is in the
    folder <code>apps/lab/audit</code>. The lab code and the lab documents name none.
  </li>
  <li>
    <strong>The fix is settled.</strong> Your answers <a href="#decision-D-AUTH-01">D-AUTH-01</a>
    and <a href="#decision-D-AUTH-05">D-AUTH-05</a> settle the fix of all 7 findings, and the record
    gives each of them the effort S.
  </li>

<aside class="note">
  <p>
    <strong>What the short form does not do.</strong> It does not hide the weakness. A reader who
    knows the sign-in library can find the token route in the public code, and the pull request that
    fixes it shows the place. The short form removes the steps for the time between the issue and
    the deploy.
  </p>
  <p>
    <strong>What cannot be taken back.</strong> GitHub says: "People with admin permissions in a
    repository can permanently delete an issue from a repository" (<a
      href="https://docs.github.com/en/issues/tracking-your-work-with-issues/administering-issues/deleting-an-issue"
      >deleting an issue</a
    >). A copy that a reader made stays. Of a pushed commit GitHub says that it can stay "In any
    clones or forks of your repository" and "Directly via their SHA-1 hashes in cached views on
    GitHub" (<a
      href="https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository"
      >removing sensitive data</a
    >).
  </p>
  <p>
    <strong>The private place of GitHub.</strong> A draft security advisory is the private form:
    "Repository security advisories allow maintainers of public repositories to privately discuss
    and fix a security vulnerability in a project" (<a
      href="https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/about-repository-security-advisories"
      >repository security advisories</a
    >). Repository owners, organization owners, security managers, and accounts with the admin role
    can create a draft, read each draft, and add collaborators to it (<a
      href="https://docs.github.com/en/code-security/security-advisories/working-with-repository-security-advisories/permission-levels-for-repository-security-advisories"
      >permission levels</a
    >).
    <span data-fact="measured">Your account has the admin role in ariakit/visonaut.</span>
  </p>
  <p>
    <strong>Limits.</strong> Nobody tested an attack. The audit opened the code for 15 of the 48
    findings and used the record for the other 33. The issue groups are not made yet, so "about 2
    issues" for the 7 findings is an assumption. Nobody estimated the days to the deploy of the 7
    fixes.
  </p>
</aside>
