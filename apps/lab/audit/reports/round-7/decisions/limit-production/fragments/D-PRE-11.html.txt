<h3 id="your-answers-reads">Five looks at the live service that change nothing</h3>

<p>
  A read is a look at the live service: a row count in the production database, or a number on a
  page of the Cloudflare dashboard. It changes no row, no check, and no pull request.
  <span data-fact="counted"
    >The audit made no such look, so five facts of this record are assumptions.</span
  >
  On 2026-10-07 you wrote: “I authorize the implementation, the GitHub writes, the two writes to
  production D1, and the package publication and the change in ariakit/ariakit.” The reads are not
  in that sentence. So one question is open: who makes them.
</p>

<p>
  The question is here because a read uses your Cloudflare login. That login can also write, and
  the account has other projects.
  <span data-fact="counted"
    >Contract line 63 lists what needs a separate instruction: “Cloud mutations, deployments,
    package publication, consumer changes, GitHub rules, and issue updates”. A read is not in that
    list. Line 188 says “No hosted diagnostic run is authorized by this contract”, and the record
    read that line as a reason to ask you (<a href="#decision-D-LOAD-02">D-LOAD-02</a>).</span
  >
  <span data-fact="counted"
    >The repository has two examples of such reads. The resource list of 2026-09-29 names its
    method: “Read-only installed Wrangler and GitHub CLI; secret names only. No external
    mutation.” (<code>docs/operations/simplification-inventory.json:3</code>). The cutover runbook
    inspects its database with “read-only commands”
    (<code>docs/baseline-delta-cutover.md:104-110</code>).</span
  >
</p>

<p>
  <span data-fact="measured"
    >Each statement ran against the 33 migrations in a local SQLite file, not against D1.</span
  >
  <span data-fact="counted"
    >Command 2 uses <code>--command</code>, as the cutover runbook does, and not

    the file: it prints totals and no count, and it warns that the database cannot serve queries
    in that time (<code>apps/web/node_modules/wrangler/wrangler-dist/cli.js:226486-226581</code>).</span
  >
</p>

<p>
  Two counts need care.
  <span data-fact="counted"
    >The second count has one more condition than the compatibility table says. A run gets its
    inventory key in a later statement than the one that creates its row
    (<code>packages/service/src/run-admission.ts:644</code>), so a run that stopped before that
    statement has no key in the form of today.</span
  >
  The count of sealed runs with no key is the count of old data.
  <span data-fact="counted"
    >The service still inserts rows into the table of the fourth count
    (<code>apps/web/src/operations/review-links.ts:224</code>).</span
  >
  So only a count of 0 decides there, and a count above 0 needs a look at the rows.
</p>
