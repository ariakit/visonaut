<h4 id="code-undecoded-images">When a pull request replaces the Submit job</h4>

<p>
  The validator is the program that opens each screenshot file and confirms that it is a real PNG of
  the stated size. Today that program is the CLI in the job <q data-no-terms>App / Visual Submit</q>
  of ariakit/ariakit. The service does not open the file.
  <span data-fact="counted"
    >It compares the number of bytes and the SHA-256 digest with the list that the same job sent
    (<code>apps/web/src/api/workflow-owned.ts</code>, lines 1038 to 1044).</span
  >
  With your answer to <a href="#decision-D-OPS-04">D-OPS-04</a>, the service no longer checks the
  workflow file.
  <span data-fact="measured"
    >5 accounts have push access to ariakit/ariakit (read on 2026-10-07).</span
  >
  One of them can edit <code>.github/workflows/app.yml</code> in a pull request and run its own steps
  in that job. Then the CLI does not run, and no program opens the files before the service stores
  them.
</p>

  <span data-fact="estimate"

<p>
  <strong>The worst realistic result with no new check.</strong> In one pull request, a reviewer
  opens a screenshot and sees an error text or a damaged picture. The check of that pull request
  stays open until a new run, or the reviewer approves a picture that is not the real screenshot.
  The service decodes no image, so no server step can fail on the bytes.
  <span data-fact="counted"
    >A decision for the whole screenshot tests only the variant that the page shows
    (<code>apps/web/src/review/review-workspace.tsx</code>, lines 385 to 394).</span
  >
  Your answer to <a href="#decision-D-WORK-04">D-WORK-04</a> also lets one decision approve changes
  that were never on screen. So a bad file can get an approval that nobody looked at. That approval
  stays in the pull request, because a run on main captures again.
</p>

<p>
  <strong>The worst case needs a second failure.</strong> A replaced Submit job must be merged to
  main.
  <span data-fact="measured"
    >The branch rule of ariakit/ariakit asks for 1 approval, a code owner review, and an approval of
    the last push (read on 2026-10-07).</span
  >
  <span data-fact="counted"
    >A run on main accepts a new screenshot with no review
    (<code>packages/service/src/local-comparison.ts</code>, lines 592 to 593 and 627), and a later
    Submit decodes the baseline image when its own image has another digest
    (<code>packages/cli/src/local-comparison.ts</code>, lines 260 to 285).</span
  >
  A real capture never has the digest of a bad file. So a bad file in the baseline stops the Submit
  of each pull request that has this screenshot, until someone repairs the baseline. Nobody tested a
  repair. A check of the bytes makes this case smaller and does not close it: the same job can send
  the test file with the filter byte, or a correct PNG with wrong pixels.
</p>

<aside class="note">
  <p>
    <strong>Limits.</strong> Nothing ran in production. The browser test used 6 small files in
    Chromium 153, Firefox 155, and WebKit 26.6 on the audit computer. The tab did not stop for the
    header of 30,000 by 30,000 pixels: each browser reported an error. No check on the server proves
    that each browser decodes a file safely.
  </p>
  <p>
    <strong>For the UI work.</strong>
    <span data-fact="counted"
      >The lab stage tests only that an image loaded
      (<code>apps/lab/src/explorations/kits/ariakit/stage/canvas.tsx</code>, line 73).</span
    >
    The review page of today also compares the size, and it turns Approve off. The review guide has
    this rule: <q>Review actions wait for the current selection's required images to load and

    bytes that are not an image, the text of today says
    <q>Check your connection and retry</q>, which names a wrong cause.
  </p>
</aside>
