  <h4 id="data-scans-old-index">One index that no statement uses</h4>

  <p>
    The poll of the review tasks is one of the statements above. The fix of the list gives it one
    more condition, and it then reads 3 rows. Migration 0030 added an index for that poll on
    2026-10-02, with pull request #190.
    <span data-fact="measured"
      >No statement selects that index, today and with the fix (local D1).</span
    >
    <span data-findings="D1-09 D1-15"></span>
  </p>

  <pre><code class="language-sql">
    -- apps/web/migrations/0030_review_queue_index.sql, the complete file.
    CREATE INDEX work_tasks_review_queue
    ON work_tasks(state, available_at, lease_until, created_at)
    WHERE kind = 'review';

    -- The removal: one new migration file. No applied file changes.
    DROP INDEX work_tasks_review_queue;
  </code></pre>

  <p>
    An index that no statement reads still costs writes. Each review decision is one task row in
    the table <code>work_tasks</code> until the server has saved it, and D1 counts 1 written row
    more for each index that a write changes.
  </p>

  <ul class="wide">
    <li>
      The 43 is 46 minus 3: a decision for 4 variants runs each of the 3 statements one time, as
      a decision for one variant does. Nobody measured that case without the index.
    </li>
    <li data-fact="measured">
      <code>DROP INDEX</code> wrote 0 rows on a local D1. A new <code>CREATE INDEX</code> writes 1
      row for each row of the table, one time: 1,001 rows for a table with 1,000 rows. So the
      removal is reversible.
    </li>
    <li data-fact="measured">
      The plan of each statement that names <code>kind = 'review'</code> is the same with and
      without the index: the poll, the promotion guard, and the deletion at the closed summary use
      <code>work_tasks_publication</code>. Round 1 measured it on a local D1. This round ran the
      same check in SQLite 3.51, two times. Nobody ran it in production D1.
    </li>
    <li data-fact="estimate">
      The saving is small: 3 rows for each decision. With 50 decisions each day that is 4,500
      rows in 30 days, which is 0.009% of the 50 million rows that Workers Paid includes.
    </li>
  </ul>
