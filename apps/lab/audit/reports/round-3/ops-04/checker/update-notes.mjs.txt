### The recommendation, challenged

- **Against option 1, a pull request from a fork:** no option gives it a check. Not a difference.
- **Against option 1, the replaced Submit job:** real, and stated. It needs push access (5 accounts) and is visible in the diff of the same pull request. - **Against option 1, a compromised action or dependency:** it cannot edit a workflow file of the run. A capture job has no token (\`contents: read\`). An action behind a tag (\`actions/checkout@v7\`) in the Submit job could send a false result in options 1, 3, and 4 alike. Only option 2 moves the Submit actions to the service.
- **Against option 1, another customer:** the signed \`repository_id\` and the audience bind a token to one project and to this service. A token of another repository was refused in the probe.
- **A hidden D1 write:** none. The service keeps no \`jti\` table (a search for \`jti\` finds only the required-claims lists). A key design writes only when a person creates or revokes a key.
- **For option 2 over option 1:** less YAML in the consumer (8 lines for 44) and an honest counting program. It stays the answer if the maintainer wants that guarantee. It can be added after option 1.
- **For option 3:** what users know, and a way out of GitHub Actions later. For Ariakit today it is not simpler than option 1 and is more to build.

Result: the change of the recommendation from \`service-workflow\` to \`no-file-check\` holds, as a recommendation. The evidence does not settle the policy question between options 1 and 2.
