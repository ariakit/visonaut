## 1. The note, and the direct answers

The maintainer wrote: "I'm starting to think that this is a problem because we opted for authenticating through OIDC, is that right? Would it be simpler if we just used API keys? Can you explore that? I think most of the existing solutions just use API keys. In that case, should we use an open-source project to manage API keys or build our own solution? Right now, we don't need much because it will be used only internally in Ariakit, but in the future we might open the service to other customers and repositories."

| Question                                  | Answer                                                                           | Why                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Is the problem a result of OIDC?          | **No.**                                                                          | The service does two things. (a) It learns who calls: the OIDC token. (b) It checks which code ran: two file hash pins. The pin cutover comes only from (b). (b) is 50 lines, `packages/security/src/oidc.ts:157-206`.                                                                                                                                                                            |
| Would API keys be simpler?                | **Simpler than today: yes. Simpler than the OIDC token with no file check: no.** | A key design has no pin cutover, but only because a key cannot do (b) at all. Removing (b) and keeping OIDC gives the same gain. For the consumer the two are then almost equal (3 permission lines and 0 secrets, or 2 lines and 1 secret; the repository already has 9 repository secrets). For the service they differ: one deletes code, the other adds a table, a page, and a new run check. |
| Do most products use a key or a token?    | **Yes.**                                                                         | 6 of 6 compared CI products accept a key. 2 of them (Argos, Codecov) also accept the GitHub OIDC token. None checks a workflow file.                                                                                                                                                                                                                                                              |
| A library or own code?                    | **Own code, if keys are added.**                                                 | Own code: 1 table, 44 lines of logic, 1 D1 read and 0 writes for each check (measured). `@better-auth/api-key` 1.7.5: 2 UPDATE statements for each check (measured). Unkey: a second system (Go, MySQL, ClickHouse, Redis, object store).                                                                                                                                                         |
| Does a key help pull requests from forks? | **No.**                                                                          | GitHub gives a fork run no secret and no OIDC token. The two proofs are equal there.                                                                                                                                                                                                                                                                                                              |

The wrong premise, corrected: the cost is not the price of OIDC. OIDC costs the consumer 3 lines `id-token: write` and no secret. The 36 pin commits of the service changed pinned values, not the identity check.

## 3. Experiments

### Experiment 1: the four situations, today and with no file check

- Question: with lines 157 to 206 of `oidc.ts` removed, and nothing else changed, does the identity check accept an honest workflow edit and still refuse a fork and another repository?
- Expected: situations 1 and 2 (edited `app.yml`, edited `ci.yml`): today refuses, the prototype accepts with 2 GitHub requests fewer. Situation 3 (replaced Submit job): today refuses, the prototype accepts. Situation 4 (fork head): both refuse at `pull.head_repository_id`. A token of another repository: both refuse at `claim.repository_id`.
- Scripts: `probe/make-no-file-check.mjs` (makes the prototype from a byte copy of `oidc.ts`), `probe/probe-four-situations.mjs` (local key set, GitHub REST stub). Run: `node --experimental-transform-types --no-warnings probe-four-situations.mjs`. Output: `evidence/probe-four-situations.out.txt`.
- Observed:

  | ---------------------------------------------- | ------------------------------------------------- | ---------------------------------- |
  | 0. No workflow edit                            | accepted; 9 GitHub requests, 2 file reads         | accepted; 7 requests, 0 file reads |

  All as expected.

- Limits: local tokens with the claim values of the documentation, and a stub for GitHub. The probe shows what the service code does with these values. ### Experiment 2: D1 writes of the Better Auth API key plugin

- Question: how many SQL writes does one key check of `@better-auth/api-key` 1.7.5 make?
- Expected (from the source): 2 UPDATE statements for each successful check, also with the rate limit off.
- Script: `probe/probe-api-key-writes.mjs`. It runs `better-auth` 1.7.5 with the plugin on SQLite in memory (`node:sqlite`) and records each prepared statement. Output: `evidence/probe-api-key-writes.out.txt`.
- Observed: the migration adds one table, `apikey`, with 22 columns. Create one key: 1 INSERT (and 1 DELETE of expired keys in the default configuration). Each of 3 checks: 1 SELECT and 2 UPDATE, in three configurations (default; `rateLimit.enabled: false`; `rateLimit.enabled: false` with `deferUpdates: true`). A wrong key: 1 SELECT, 0 writes. The stored value is a hash of 43 characters, not the key of 64 characters. As expected.
- Limits: SQLite in memory, not D1. Better Auth sends the same SQL to D1 through its Kysely adapter. The probe counts statements; D1 bills rows written, which is 1 row for each of these UPDATE statements when no index covers the changed column. Not tested: the `secondary-storage` mode.

### Experiment 3: a key check with own code

- Question: what does a key check with own code cost in D1, and how many lines is it?
- Expected: create 1 INSERT, check 1 SELECT and 0 writes, revoke 1 UPDATE.
- Script: `probe/probe-own-key.mjs` (one table `project_keys`, SHA-256 of a key of 32 random bytes, lookup by hash, a comparison in constant time). Output: `evidence/probe-own-key.out.txt`.
- Observed: create `{"INSERT":1}`; each of 3 checks `{"SELECT":1}`; a wrong key 1 SELECT; a text that is not a key 0 statements; revoke `{"UPDATE":1}`; a check after the revoke gives no project. The key logic is 44 lines without empty lines. As expected.
- Limits: this is a prototype of the logic, not service code. The estimate of the rest (below) is not measured.

## 4. What an API key design needs

- Consumer: 1 repository secret (`VISONAUT_API_KEY`; `VISONAUT_TOKEN` is taken) and 2 `env` lines (the Plan step of `ci.yml` and the Submit job of `app.yml`). `ci.yml:92` already passes each secret to `app.yml`. The 3 lines `id-token: write` and the variable line go away.
- Service table: `project_keys (id, project_id → visonaut_projects.id, key_hash UNIQUE, prefix, name, created_by, created_at, revoked_at)`. No "last used" column and no counter: each would be a write for each request.
- Create, show one time, list by prefix, revoke: a new part of the settings page, for a repository administrator. Create and revoke are 1 D1 write each, by a person. Replace: create a second key, change the secret, revoke the first.
- Check: 1 D1 read for each request; 3 requests for a run with captures, 1 for a no-visual report.
- The run: the run number, the attempt, and the commit are then unsigned values of the request. The service must check them through the GitHub App (the run is a run of the project's repository, the attempt is the newest, the head commit matches, the pull request is open). It cannot learn which job sent the request: the `check_run_id` step and the primary key of `transfer_key_redemptions` (`apps/web/migrations/0018_transfer_key_redemptions.sql`) change.
- The GitHub App stays (D-AUTH-02, `keep-one-app`): it writes the check, and the service reads GitHub through its installation.
- Key to repository: `project_keys.project_id` to `visonaut_projects.repository_id`. Later customers: one project row and one installation for each repository, in each design. With the OIDC token the signed `repository_id` gives the project directly.
- Estimate of the work (not measured): key logic 44 lines (measured in the probe), a migration of about 12 lines, 3 routes with a permission check, a settings part, a CLI change, and a rewrite of the run binding of `oidc.ts:207-336` to take the run from the request. Roughly 300 to 400 new lines plus tests. Option `no-file-check` deletes about 50 lines in `oidc.ts` and the pin comparisons in 6 more files.

### Recommendation and what would make it wrong

Recommend `no-file-check`. This changes the r2 recommendation (`service-workflow`). Reasons:

1. It gives what the note asks from API keys (no cutover, a workflow edit is a normal pull request) with 0 secrets, no key page, and no key table.
2. It is the least to build: it deletes code. r2 said the same ("Option 1 is less to build").
3. New evidence of this round: every compared product has this trust model, and 2 of them use the same token for it.
4. New fact of this round: other customers later. A file check for each customer does not scale, and the signed `repository_id` binds a run to one project with a column that exists.
5. It closes no door: `service-workflow` and API keys can both be added later.

r2 kept the guarantee "a pull request cannot replace the Submit job" as the default because the earlier decision A02 had selected a pin model. The note of this round points the other way, to a design (API keys) that cannot give that guarantee at all. So the question for the maintainer is now explicit in the rationale of the decision: is the review of a pull request enough protection?

It is wrong if:

- A pull request must not be able to replace the program that counts. Then `service-workflow`.
- An account with push access to `ariakit/ariakit` is not trusted with the result of the visual check.
- A customer needs a CI system other than GitHub Actions. Then keys, with own code, as a second proof.

### The recommendation, challenged

- **Against option 1, a pull request from a fork:** no option gives it a check. Not a difference.
- **Against option 1, the replaced Submit job:** real, and stated. It needs push access (5 accounts) and is visible in the diff of the same pull request. The same accounts have a less visible way today (capture code, TRUST-03). So the file check buys little for its cost. This is a policy question, and the decision asks it.
- **Against option 1, a compromised action or dependency:** it cannot edit a workflow file of the run. A capture job has no token (`contents: read`). An action behind a tag (`actions/checkout@v7`) in the Submit job could send a false result in options 1, 3, and 4 alike. Only option 2 moves the Submit actions to the service.
- **Against option 1, another customer:** the signed `repository_id` and the audience bind a token to one project and to this service. A token of another repository was refused in the probe.
- **A hidden D1 write:** none. The service keeps no `jti` table (a search for `jti` finds only the required-claims lists). A key design writes only when a person creates or revokes a key.
- **For option 2 over option 1:** less YAML in the consumer (8 lines for 44) and an honest counting program. It stays the answer if the maintainer wants that guarantee. It can be added after option 1.
- **For option 3:** what users know, and a way out of GitHub Actions later. For Ariakit today it is not simpler than option 1 and is more to build.

Result: the change of the recommendation from `service-workflow` to `no-file-check` holds, as a recommendation. The evidence does not settle the policy question between options 1 and 2.
