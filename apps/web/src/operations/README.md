# Operations integration

Apply the numbered web D1 migrations, including the history, retention, and grouped-backup migrations through `0012_historical_comparisons.sql`. Call `runOperations(context, exporter)` after authenticated ingest reconciliation. Schedule it at least every five minutes. If `hasMore` is true, publish an operations continuation instead of waiting for the next cron tick. Queue consumers can repeat delivery; D1 task identities and leases control all durable effects.

```ts
const exporter = createCloudflareDatabaseExporter({
  accountId: env.CLOUDFLARE_ACCOUNT_ID,
  databaseId: env.D1_DATABASE_ID,
  apiToken: env.D1_BACKUP_API_TOKEN,
  maximumMilliseconds: measuredExportDeadline,
});
const result = await runOperations(context, exporter);
if (result.hasMore) await operationsQueue.send({ kind: "continue" });
```

Set every `OperationsBudget` field from measured deployment limits. Keep the lease longer than the maximum database export operation and a page of verified copies. `maximumExportEntries` limits one archive. Set the web Worker's `limits.subrequests` above this limit plus authentication and metadata overhead. The download prefetches at most four objects and cancels readers when the client disconnects. A local fixture is not evidence of remote R2 download performance: measure the full 10,580-capture export with references and derived images before launch.

Database history survives image expiry. The scheduler samples physical database bytes from D1 `meta.size_after` and counts uploading or comparing runs. The private dashboard shows the sample time, physical usage, admission headroom, and active capture count. Configure `databaseWarningBytes`, `databaseAdmissionBytes`, and `maximumActiveRuns` in `VISONAUT_API_LIMITS`. Physical admission must remain below D1's hard database limit. Select thresholds with measured headroom for concurrent capture work.

New run identities are refused when a fresh physical sample reaches the admission threshold. A missing physical sample also refuses new admission. The active upload/comparison count is checked again inside the run reservation transaction. Ready reviews do not use a capture slot, so later full main captures can proceed while older reviews wait. Replays of an existing workflow attempt remain available. Capacity warnings clear after a healthy sample falls below the warning threshold. This is a pause safeguard, not a strict byte quota or a promise of sustained throughput. It does not delete permanent identity, decision, or review history.

`POST /api/runs/:runId/export` calls `createRunExport(context, { runId, actorId })` and returns `{ exportId, downloadPath }`. `GET /api/exports/:exportId` calls `streamRunExport`. Both routes must require a current maintainer session and live repository authorization. The GET response is a private TAR stream. A sealed, ready comparison is required. It includes current and inherited candidate images, protected reference originals, profiles, provenance, raw manifests and plans, decisions, commands, audit metadata, and a final `complete.json` integrity marker. Keep metadata private even when validated image routes are public. Exports expire after 24 hours; an active download can finish within its one-hour lease. A truncated archive has no valid completion marker. A failed operation does not release unrelated review, manual, or baseline pins.

Export format 2 stores a small `metadata.json` root and immutable pages. The root lists each page's TAR name, byte count, and SHA-256. Metadata pages contain `{ version: 2, runId, section, rows }`; capture rows contain their full profiles. Entry pages use the same envelope with `section: "entries"` and list the image or source files that follow. The writer reads about one MiB of SQL records at a time and writes at most 100 rows per page. A larger single row must fit the configured object limit. The root is limited to two MiB, and total metadata and object counts remain subject to deployment budgets.

The provisional 200,000-entry bound covers four image objects for each of 40,000 admitted captures: original, thumbnail, mask, and protected reference, with room for history documents. The 35,820-capture inventory alone can contain 143,280 such image entries. The web Worker allows 250,000 subrequests so the download can read those objects and its bounded metadata pages. Cloudflare permits a configurable paid-plan limit above the default. These are finite shape bounds; complete hosted export time, CPU, and cost remain launch gates. [Worker subrequest limits](https://developers.cloudflare.com/workers/platform/limits/#subrequests).

During download, the service verifies each page and each source object before it emits completion. Checksum pages at `checksums/000000.json`, for example, map exported file names to SHA-256 values. The final format-2 `complete.json` lists the exact checksum-page names, sizes, and digests, plus the payload entry count. A reader must verify those pages and all listed files; the presence of a completion filename alone is insufficient. Existing format-1 exports can still be downloaded until they expire. Expiry removes private export pages in bounded steps before it releases export-owned pins.

[D1 Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/) remains available for an emergency database rollback. The scheduler finishes any SQL-plus-R2 backup that was already exporting or copying when this policy changed. It does not start new backup sets. Existing completed sets remain available until their 30-day retention expires. Time Travel rewinds D1 in place within Cloudflare's retention window; it does not restore missing R2 images or provide an independent copy. A run export remains available for important visual evidence while its source images are retained.

The following backup implementation remains for unfinished and retained legacy sets. Those sets used the D1 SQL export API and immutable 12-hour UTC slots, such as `2026-09-22T00Z` and `2026-09-22T12Z`. The scheduler resumes an unfinished set by its exact identifier. Atomic creation and export leases prevented overlapping sets.

Backups pin live runs before exporting and refresh those pins after the snapshot to cover runs created as the export starts. A backup cannot begin during an irreversible original-image, protected-snapshot, or backup-group deletion. The guarded export-completion transaction freezes group identities. Recovery pins and the snapshot-deletion guard preserve required bytes while the backup runs.

Manifest version 3 stores immutable groups for sealed runs, completed comparisons, protected snapshots, and verified history archive generations. A ready history archive supplies its fixed derived-image list; a later historical comparison gets a separate supplement and group. Unsealed runs and comparisons that are still running use a backup-specific generation. Each group has content-addressed object-list pages and a checked root in R2. A warm backup reads group records and writes its membership pages. It has no permanent per-object D1 registry and does not list the source buckets.

For example, consecutive snapshots reuse the group containing `runs/run-42/originals/image-7`. The same bytes at `runs/run-43/originals/image-7` belong to another run group. This is not cross-run byte deduplication. The first copy verifies source and destination bytes; restore verifies them again. Only backup garbage collection may remove private backup objects. Do not add a bucket lifecycle rule or another writer that can delete or replace `backup-groups/` or legacy `backup-objects/` keys.

Copy pages run at most six operations at once. They wait for all started copies before advancing the durable cursor or releasing the lease. Known-length streams use `FixedLengthStream` at the native R2 boundary. Unknown-length SQL uses multipart upload with one 8 MiB buffer and aborts unfinished uploads on failure. The configured database-byte limit applies to both paths. Grouped backups require `objectsPerStep` from 2 through 1000.

`complete.json` is written conditionally only after all required groups and membership pages are durable. Pages include their content digest in the key, so a stale lease holder cannot replace a later owner's inventory. Only a successful guarded completion extends each referenced group's lifetime to 30 days after completion plus a 24-hour deletion grace. A failed or incomplete backup cannot advance completed ownership. SQL snapshots and their membership pages expire after 30 days. Group deletion claims block a new backup until deletion settles; an expired lease lets a later invocation finish a crashed deletion. Each group has a unique generation prefix, so a delayed old delete cannot remove a replacement group. Temporary D1 page and membership rows are removed after completion.

Existing date-only version 2 and 3 backups can finish with their original identifiers. Date-only version 1, 2, and 3 restores remain supported. The common expiry path accepts both date-only and half-day identifiers. Old shared objects expire through the legacy collector; version 3 groups use a separate prefix and collector. Before completion publication, repeated failed attempts terminalize the backup and atomically release its temporary memberships and recovery pins. An ambiguous completion-marker write stays fenced for reconciliation. Private `operations_events` report failures. The scheduler resolves any old backup-age alert because new SQL snapshots are no longer scheduled.

Retained sets expire 30 days after completion. Backup object retention continues to run, so the old R2 objects and D1 rows leave through the existing guarded collector. Do not manually delete backup records, objects, or recovery pins.

Required plans and manifests are copied from QUARANTINE while their live database pointers exist. Closed-run archives preserve their exact original bytes in the private `documents` section. Ready run and comparison archives live under IMAGES `history/`; include their manifest and every page in backup coverage. Restore removes unfinished archive pointers and keeps verified ready archives. Do not apply upload lifecycle expiry to live `plans/` and `manifests/` prefixes.

Schedule `expireComparisonReferences(context)` before `expireSnapshotImages(context)`. The first phase releases expired outgoing comparison references. The second revokes an unrooted snapshot's reference eligibility, waits the guarded grace, then deletes only its unique `baselines/<snapshot>/` prefix. Current and rollback baselines, active comparisons and reviews, exports, manual pins, and recovery work block the relevant transitions. Original byte settlement must use `completeRetiredRunDeletion`; it releases inherited owners only after dependent bytes are gone. Archive readiness gates detail and byte cleanup. The collectors use bounded pages and saved cursors so blocked old records do not starve later candidates.

The private dashboard displays unresolved attention items; this module sends no external messages. Exhausted comparison work appears in the service's failed status. A failed or ambiguous GitHub POST/PATCH stays fenced. An ambiguous creation can reconcile by its exact App/SHA/external identity. Never clear an ambiguous PATCH solely because its lease expired or because a GET currently looks correct.

To restore a retained legacy set, call `restoreBackup(backupStore, backupId, isolatedTarget, limits)` with its exact identifier. The target must reject a nonempty database or bucket, import the SQL into an isolated database, apply current rules, and verify every database reference before activation. `sanitizeRestoredDatabase` supplies the default session/token cleanup and fences old work; old runs are inactive, incomplete snapshots are revoked, and saved external deliveries cannot restart. Rotate Better Auth and ingest capability secrets in the restored environment before activation. The restore event remains unresolved until that deployment step is complete. Keep the original database and buckets untouched during the drill.

A D1 Time Travel rewind is not a complete Visonaut restore. It leaves R2, GitHub checks, queues, and Worker secrets at their current state while D1 moves backward. Stop service traffic and queue consumers before a rewind. This repository has no tested procedure to reactivate an in-place restored database. Keep the service offline afterward until sessions and stored account tokens are invalidated, pending work and external GitHub deliveries are fenced or reconciled, D1 references and foreign keys are checked against retained R2 bytes, and application secrets are rotated. Do not run `sanitizeRestoredDatabase` on live D1: it is designed for an isolated target and deletes backup records and pins.

The tests use real SQLite transactions and the native Worker/R2 runtime, stream original bytes through TAR, restore a SQL snapshot into an empty SQLite database, and inject storage and GitHub failures. They cover missing protected originals, corrupt bytes, lost POST/PATCH responses, revised intents, exhausted leases, owner pins for inherited captures, and exact retention prefixes. The native grouped-backup test also removes all live source bytes, restores into new D1/R2 bindings, checks foreign keys and byte digests, and measures cold versus warm operation counts. Its optional 1000-object inventory fixture uses small synthetic bodies; it does not prove hosted latency or a full capture workload. Remote restore and large download drills remain deployment checks. A version 2 drill is evidence for that implementation only; the grouped implementation needs its own measured restore evidence before launch.
