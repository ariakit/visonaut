# Image-bearing production backup restore

The scheduled production backup `2026-09-25T00Z` was restored into an isolated D1 database and two isolated R2 buckets. The source production database, buckets, and Workers were not changed. The [backup receipt](./e08-production-image-backup-20260925.md) verifies the completion marker and 172,982,389-byte SQL export. This [sanitized restore receipt](./e08-production-restore-20260925.json) records the target IDs, aggregate counts, and limits without publishing image bytes, SQL, object keys, or credentials.

The immutable marker identifies seven groups, 2,055 object entries, and 128,032,891 object bytes. All 2,055 entries were fetched from the production backup, checked against their inventory hashes, and copied to isolated image and quarantine buckets. Each target object was read back after upload and checked for byte length, SHA-256, and content type. The completed checkpoint contains 2,055 distinct verified identities and the same marker hash. The local inventory replay completed in 9.181 seconds after its source objects were already cached; that duration is **not** a hosted recovery time.

The SQL export was imported into isolated D1. Five large JSON fields in three rows exceeded the import statement limit. The import used short placeholders for those fields, then restored their exact source values with bound updates and readback checks. A fresh read-only target check on September 25 compared the main row counts with the verified local SQL copy: 1,986 images, 1,058 captures, 3,174 comparison rows, 3,642 staged images, and 10,864 webhook-delivery rows matched. `PRAGMA foreign_key_check` found no violations. Sessions, active runs, and stored account tokens were zero in the target. Backup-operation rows, verification records, review sessions, and rate limits were deliberately not carried into the isolated target.

This is a full object and database restore of the first image-bearing production backup. It does not establish a measured end-to-end RTO: the remote D1 import, R2 replay, checks, access reapplication, and credential rotation were not timed as one operation. The isolated target was not activated. The [separate capacity drill](./e08-capacity-restore.md) did measure an 11m19s RTO with credential rotation on a synthetic 7,414-object corpus. The production backup is one observed scheduled slot after the full Ariakit capture. Sustained real-time scheduling under that workload remains open for the 24-hour RPO claim. E08 remains partial until those limits are resolved.
