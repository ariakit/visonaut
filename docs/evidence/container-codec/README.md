# Hosted Container codec probe

On September 22, 2026, a deployed `visonaut-e01-container-probe` ran the same PNG/WebP comparison contract with native Sharp and the Worker WASM codec. The probe used one Cloudflare `lite` Container instance per run. This is a codec and lifecycle probe, **not a production comparison fallback**. It has no production queue, R2, D1, or access-control bindings.

[The curated receipts](./hosted.json) retain all 98 request outcomes, selected digests, per-request time, process high-water readings, lifecycle state, and seven Cloudflare Container Analytics minute groups. [The fixture index](./fixtures.json) records input sizes, SHA-256 values, and expected responses. The [curator](../../../tooling/evidence/container-codec/curate.py) validates fixture outcomes and native/WASM parity from the original local receipts; its output omits probe URLs, instance IDs, and boot IDs. SHA-256 values in the curated file identify those original JSON receipts, which are not published. The deployed Worker source and Container server source had SHA-256 `79c7bd4c618f47a0b9cba2757eee33c4ea47fbfc0f0bc7e9a3640a74cfa6dbce` and `b9a81e6aaca6951df063fd9e69880f1bb3c87532e02caf9c7d819079a53dc516`, respectively. The Container image digest was `961ec65a3cebd3e9ac324f41242442baa6d608202644207315dc41166db94fc1`.

The repeat set made five passes each over the 1248 × 1650 PNG and WebP and the 1400 × 1500 decoded-limit PNG, with one unchanged and one all-pixels-changed comparison in each pass. Native and WASM returned the same status, changed-pixel count, decoded-pixel digest, thumbnail digest, and mask digest in every paired case. Every request in each serial run reported one boot ID. A separate lifecycle probe returned HTTP 200, explicitly stopped its instance, then served a new request under a different boot ID; it ended stopped.

The Linux `resourceUsage.maxRSS` values are **process** high-water marks in KiB, not Container memory peaks or Worker isolate peaks. `/sys/fs/cgroup/memory.peak` and related memory files returned `ENOENT` in every recorded successful comparison. Cloudflare Container Analytics reported seven minute groups and a sampled maximum memory value of 336,760,832 bytes. That sample exceeded the nominal 256 MiB `lite` instance size, so neither the nominal size nor these counters should be treated as an enforced peak or proof of safe production headroom. The analytics value is not a continuous peak. The `wasmLinearMemoryBytes` maximum was 38,076,416 bytes and likewise excludes other memory.

Cloudflare [lists `lite` as 256 MiB](https://developers.cloudflare.com/containers/platform/limits/) and [bills provisioned Container memory, active CPU, and disk](https://developers.cloudflare.com/containers/platform/pricing/), in addition to its Worker and Durable Object use. This first probe has no measured production duty cycle, cold-start distribution, Queue retry behavior, R2/D1 I/O, concurrent load, or full monthly cost.

The later [integrated diagnostic record](./hosted-queue.md) covers the actual Queue → comparator Worker → native Container → R2/D1 path on the synthetic repository. It proves first-attempt completion, changed-pixel masks, and an inactive instance after work. Production and preview still select the Worker codec. The integrated record also retains the failed idle-lifecycle probe and its repair; it does not turn sampled memory into a peak or establish the full workload and monthly cost limits. E01 remains partial until those bounds and the production fallback deployment are verified.
