# Hosted Container capacity with the Ariakit image-size matrix

E01 remains **partial**. On September 23, 2026, the diagnostic comparator completed 3,583 changed-image pairs through its D1 task queue, Queue consumer, Worker, private `basic` Container, R2 originals and derived artifacts, and D1 result commit. The originals were 3,582 private PNGs from one measured Ariakit pass, plus one 1,400 × 1,500 admissible boundary PNG. Each candidate changed one pixel, except the boundary candidate, which changed all 2.1 million pixels. This is a representative image-size workload with controlled differences, not a trusted Ariakit upload or a natural pass-to-pass result distribution.

The diagnostic Worker version was `c75ee0f5-0ab2-4fde-87ef-b657724ffb3d` with the production-source native Container image `sha256:1e66a2ca2e144fe4e5a2526e70c03624b5bf9fd2f73a99e34023ac99fd9840a3`. The Container used Sharp 0.35.4 and libvips 8.18.6. Production and preview retained `VISONAUT_CODEC_BACKEND=worker`; this probe did not change their routing or launch state. Its private injector bypassed GitHub admission and the public upload path while retaining the service's run, seal, snapshot, comparison, task, and artifact commits.

The [sanitized C1 receipt](./full-matrix-c1.json) comes from the listed private D1 final result, Cloudflare Analytics snapshots, archive verification, Queue quiescence, cleanup, and diagnostic-health receipts. The [curator](../../../tooling/evidence/container-codec/curate-full-matrix.py) validates their identities and counts, then removes task IDs, instance IDs, object keys, image bytes, and account identifiers. Its SHA-256 entries identify the private originals; the raw originals are not published. The fixture manifest SHA-256 was `d14bc1eb01a240703f4aad30acecf06f3ad5e18f5aaec2d760155c5388255f6a`.

Task latency includes Queue waiting, scheduled duplicate publication, Worker and Container work, and result commit. It is not isolated codec latency. The first unique hosted Queue delivery occurred at 06:55:24 UTC, and the last unique D1 completion at 12:12:42 UTC, about 5h17m apart. The Queue was configured for one consumer and one Container lane. Cloudflare's resource-scoped Analytics recorded 9,992 writes, 9,559 reads, and 8,851 deletes through the unique-completion window; the later drain snapshot recorded 9,992 writes, 10,582 reads, and 9,883 deletes. Scheduled reconciliation republished pending tasks while the backlog drained. These operations are real usage, but they cannot be equated with unique comparisons or with an invoice.

The Container metrics are samples. Cloudflare reported 295,636,992 bytes as the highest sampled memory value, including the minute when the all-pixel boundary comparison completed. It is not a continuous process or full Container peak. Linux process RSS was not instrumented in this production image, and the earlier codec-only probe could not read `/sys/fs/cgroup/memory.peak`. The 295 Container metric and usage minute groups also cannot establish active duty: some nominal one-instance minute groups report more than 60 GiB-seconds of provisioned memory. The raw active-window totals were 20,266,780,027,453 provisioned-memory byte-seconds, 75,499,639,017,332 provisioned-disk byte-seconds, and 265.88 usage CPU seconds. [Cloudflare describes metrics and usage as separate datasets](https://developers.cloudflare.com/analytics/graphql-api/tutorials/querying-container-metrics/), with usage including its sandbox. A direct conversion from those minute groups to duty would overclaim the observation.

All 14,332 source and derived objects were copied into a separate private archive, then reread and SHA-256 verified. After three zero-backlog and empty-peek observations over 154 seconds, the synthetic D1 project was removed with a scoped plan; unrelated diagnostic rows were preserved apart from a concurrent scheduler event update. Authenticated diagnostic `/api/operations` returned HTTP 200 after cleanup. Source R2 deletion remains incomplete and is **not** required for the separate capacity measurement: 137 pages of 50 objects were removed before the approval stop, and the rest remain under the original source prefix. The complete, verified archive retains the evidence. No further source deletion is part of this probe.

## Isolated four-lane follow-up

The second probe used a dedicated D1 database, four Queue lanes with one consumer each, a dead-letter Queue, an isolated Worker, and at most four `basic` Containers. The private R2 bucket is separate from production and diagnostics, but also holds the preserved first-run archive under disjoint keys. Its Worker version was `9e91aca2-b443-4852-b9dd-bb042a4a1477`; the pinned production-source native image was `sha256:d9a359f4da61d3c25c711ffb3793295dea05a0ec85e1b120537829fc64780ae6`. It used the same 3,582 Ariakit pass-1 PNG originals with controlled one-pixel candidate edits and one 1,400 × 1,500 full-change boundary pair. Source PNG sizes had median 10,572 bytes, p95 41,218 bytes, and maximum 1,668,228 bytes. This was not a trusted upload or natural change distribution. Production and preview continued using the Worker codec.

The [sanitized four-lane receipt](./full-matrix-scale4.json) joins the private fixture, publication, D1 final state, direct R2 read-back, Queue quiet window, stop, archive, and scoped Analytics receipts. Its [curator](../../../tooling/evidence/container-codec/curate-scale4.py) verifies the run identities, bounded Worker configuration, counts, SHA-256 relationships, and chronology before omitting task IDs, object keys, instance IDs, and account identifiers.

The final D1 verification checked each ordered task, expected changed-pixel count, codec version, generated image ID, and terminal state. It also found all four Queue backlogs at zero and 14,332 complete image records totaling 127,363,651 bytes. The separate quiet-window check found zero backlog and empty peeks in all five isolated Queues. The four consumers were then paused, and the authenticated stop route returned HTTP 200 with all four Container states `stopped`, before the three-hour deadline. Two independent host-local stop processes remained alive at close. This establishes an observed stop, although host-local watchdogs alone would not guarantee a stop if the machine became unavailable before a future deadline.

The live Worker tail captured 3,519 of 3,583 unique native fetches and reconnected seven times, so its timing distribution is a sample. The 3,520 recorded native responses were HTTP 200; their fetch-time p50, p95, and maximum were 249 ms, 530 ms, and 10,013 ms. First observed fetches in each lane took 2,154–2,930 ms. The subsequent observed fetches include work after process restarts and cannot be treated as a pure warm-start distribution. D1 task latency includes Queue wait and result commit, while the schema does not retain a separate per-task Queue wait duration. The tail showed one task-level error and two canceled invocations. D1 recorded three retried tasks and all tasks ended correctly; the tail does not prove a one-to-one mapping from errors to retries.

Node process `maxRSS` high-water marks were 208,711,680, 219,168,768, 221,212,672, and 207,675,392 bytes by lane. The process-uptime series showed at least one restart and had a 62.777-second observation gap when a cached Cloudflare OAuth token was rejected. `/sys/fs/cgroup/memory.peak` was unavailable. Cloudflare Analytics reported 279,851,008 bytes as its highest sampled Container memory value across four instance IDs. None of these readings establishes a continuous full-Container peak. Its `containerUptime` sum was zero during active work and later reported a large cumulative-looking value, so it cannot establish an exact active duty cycle here.

The resource-scoped Analytics interval ran from 16:54 to 18:03 UTC, covering the comparison and verified stop before the separate R2 content audit. It reported 341.88 Container usage CPU seconds, 16,632,240,959,434 allocated-memory byte-seconds, 61,959,925,887,860 allocated-disk byte-seconds, and 25,791,075 transmitted bytes. At [Cloudflare's published Container overage rates](https://developers.cloudflare.com/containers/platform/pricing/), CPU plus memory plus disk has a **$0.049900 rate equivalent** for this probe before monthly allowances. This is not the account's incremental bill: shared allowances, Worker/Durable Object/Queue/D1/R2/log charges, and egress are outside that figure. The [E07 account cost study](../e07-cost-admission.md) has no invoice-aligned billable-usage readback for this probe. [Cloudflare's usage dataset includes its sandbox](https://developers.cloudflare.com/analytics/graphql-api/tutorials/querying-container-metrics/), and its adaptive datasets can report [estimated operation totals](https://developers.cloudflare.com/analytics/graphql-api/sampling/).

The 18:05 and 18:15 queries of the same interval returned identical totals, but Queue deletes (3,569) and R2 puts (6,972) remained below the exact terminal task and derived-object counts (3,583 and 7,166). These adaptive figures are resource usage estimates, not an artifact ledger. The 7,166 original R2 uploads happened during seeding before this interval, while the D1 and Worker totals in it include measurement traffic. All 14,332 new-run R2 objects were reread and SHA-256 checked against their D1 digests, and an exact R2 listing matched the verified manifest. The frozen first-run archive inventory was also re-listed after the probe. Its 14,332 keys, 127,363,651 bytes, and inventory SHA-256 matched the pre-probe receipt; this after-probe archive check was an inventory check, not a second full content rehash. The one-lane and four-lane results still do not certify the issue's 10,580-capture design target or 35,820-capture stress workload.
