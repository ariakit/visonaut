# Production capacity admission, September 28, 2026

At 09:48 UTC, [Ariakit Submit job 108873879481](https://github.com/ariakit/ariakit/actions/runs/36402891873/job/108873879481) received `capacity_exceeded` from `POST /v1/runs`. The service counted zero active upload or comparison runs against its five-run limit. It refused the new identity because D1 reported 810,733,568 physical bytes against the provisional 805,306,368-byte admission limit. The latest _completed_ SQL backup was 460,669,026 bytes against the separate 536,870,912-byte limit. The number of open pull requests did not cause this failure.

The backup for the 2026-09-28 00Z slot was still copying at 10:05 UTC. Its already exported SQL snapshot was 652,154,314 bytes, above the old SQL admission limit. The completed-backup sample therefore understated current SQL size. The in-progress backup held recovery pins for 83 runs; 14 closed pull-request runs had not yet archived their detail, and all 14 had one of those backup pins. The backup had no recorded failure at this observation. It releases its recovery pins when it completes or fails; this note does not claim it had completed.

Processed GitHub webhook receipts are a large, measurable source of SQL growth. D1 held 30,566 delivery rows, of which 30,562 were processed. There were 25,452 processed `check_run` receipts and 4,020 processed `workflow_run` receipts. A sample of the latest 1,000 deliveries found mean payload sizes of 13,153 bytes for 799 `check_run` rows and 20,098 bytes for 162 `workflow_run` rows. Applying those sample means to the full event counts suggests about 335 MB and 81 MB of JSON respectively. These are estimates, not exact table sizes. A full `SUM(LENGTH(payload_json))` query failed with a D1 internal error, and D1 rejected `PRAGMA page_count` and `PRAGMA freelist_count`, so this observation cannot assign the remaining physical bytes to live rows, indexes, or free pages.

The interim policy warns at 1.5 GiB physical D1 or 1 GiB in the latest completed SQL backup. It pauses new run identities at 2 GiB physical D1 or 1.25 GiB SQL. The SQL stop remains 768 MiB below the configured 2 GiB backup exporter maximum; the physical stop remains more than 7.8 GB below D1's 10 GB database limit. The five-active-run limit and image-size limits remain unchanged. These stops provide room for the observed service state while processed webhook bodies are addressed separately. They are not a sustained-growth or cost guarantee.

This SQL-size stop was an interim response. The later [backup scheduling policy](../../../apps/web/src/operations/README.md) ends new scheduled SQL backups and removes their stale size from admission. The 1.5 GiB physical warning and 2 GiB physical admission stop remain active.

The measurements came from read-only `wrangler d1 execute visonaut-production --remote --env production` queries of the capacity cursor, `operations_backups`, grouped `visonaut_runs`, grouped `github_webhook_delivery`, and a 1,000-row recent payload sample. Observe physical size and actual admission during ordinary runs after the backup-scheduling change deploys. The earlier request to measure the next SQL backup no longer applies. Do not delete receipt identities or unprocessed payloads to reclaim space.
