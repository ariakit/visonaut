# Hosted failed-job inheritance on the diagnostic service

On September 23, 2026, public synthetic [PR #19](https://github.com/ariakit/visonaut-diagnostics/pull/19) ran two Chromium capture shards against tested PR merge commit [`2b2c95e8`](https://github.com/ariakit/visonaut-diagnostics/commit/2b2c95e8b12197d86502e4586c49ed452c4e9f53). The fixture head was `9120f50400e66b3f71e9f83508efab05cd36ee6c`. Its trusted reusable workflow was pinned to `b37defd0ddcfabfce864511b31def1e9a27c67e3` and its executor source to `756a5225af9bbcd466ef56d56abdee2843b897c9`. The service was the diagnostic web Worker at version `75c8f8c7-ed01-4f50-83bf-528be27433b5`, deployed at 100% traffic from Visonaut source [`57f5687`](https://github.com/ariakit/visonaut/commit/57f5687b94b0fba4b22a1bc1d8c2b5c3133251a9). Later implementation commits changed the Ariakit workflow pin and documentation, not this diagnostic service code.

The first attempt of [workflow run `35811335129`](https://github.com/ariakit/visonaut-diagnostics/actions/runs/35811335129) finished shard 1 successfully (job `107023374998`) and failed shard 2 as the public fixture requested (job `107023375041`). Before the rerun, the diagnostic database showed one complete shard with one capture and one pending shard with no capture. The service marked that incomplete attempt `failed`; it did not seal or compare it.

GitHub's **rerun failed jobs** operation created attempt 2 at the same tested SHA. It carried shard 1 as a success alias (`107023761300`, original start and completion times) and ran only shard 2 again (`107023760350`). The workflow completed successfully. Visonaut's active run `02e68913-0d6c-45ca-858f-9f32b53b6519` recorded:

| Shard        | Source run attempt | Manifest source                                                   | Stored capture retry |
| ------------ | -----------------: | ----------------------------------------------------------------- | -------------------: |
| `chromium-1` |                  1 | Original successful shard; same manifest and full profile digests |                    0 |
| `chromium-2` |                  2 | Newly successful rerun shard and independent discovery artifact   |                    1 |

The second test deliberately captured red on Playwright retry 0 and green on its successful retry 1. Only the retry-1 capture appears in the sealed comparison. Its candidate image digest `9c7bc79a317fd2dbe8f0a1e860ce91888ceb8275d1a9f69fc9245b93c5f4d6af` matches the green reference; the comparison counted zero changed pixels. The service did not silently accept it because its capture profile digest changed from `ab33a8c2…` to `ce5a245f…`. The [Visonaut App check on the tested commit](https://github.com/ariakit/visonaut-diagnostics/commit/2b2c95e8b12197d86502e4586c49ed452c4e9f53/checks) first reported failure while one variant needed review. The signed-in maintainer compared the two green synthetic cards in the [deployed review](https://diagnostics.visonaut.com/runs/02e68913-0d6c-45ca-858f-9f32b53b6519), saw the profile change and zero-pixel result, and approved that variant. The UI then reported zero variants needing review and “Check passed.” The same App check `107024022145` reported `success` at 02:47:23 UTC. This was one status transition on the exact tested merge commit, not a status injected by a diagnostic sender.

The [sanitized receipts](./failed-job-final.json) contain the two GitHub job lists, independent receipt-artifact metadata, D1 run/shard/capture rows before and after rerun, comparison identities, App check states before and after approval, and browser observations. The before-state values were transcribed from read-only D1 and GitHub responses captured during this task before the rerun and approval; those mutable endpoints now return the later states. The local fixture's 11 Node tests passed before this hosted run. The receipts omit OAuth tokens, URLs with credentials, manifest contents, image bytes, and private Ariakit data.

This proves failed-job inheritance, Playwright retry selection, profile-sensitive review, and App status recovery for one synthetic pull request on the deployed diagnostic source. It does not replace the separate full Ariakit service cycle, production baseline, all profile combinations, or the required-check cutover. PR #19 is a probe; its first-attempt failure flag must not be merged into the fixture's main branch.
