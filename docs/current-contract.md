## Current path and evidence state

W01 of [issue #204](https://github.com/ariakit/visonaut/issues/204#w01) established this guide on 2026-10-02. The [2026-10-03 completion record](history/evidence/issue-204-completion.md) records the later selected implementation, releases, adoption, production removals, and remaining limits. Read the [18 selected decisions and full appendix](https://github.com/ariakit/visonaut/issues/204#issuecomment-5956746624) for their conditions. Earlier source counts and test totals retain their original snapshot scope.

The normal visual path is:

```text
Playwright capture -> trusted CLI comparison -> service validation
-> maintainer review when required -> GitHub App status
```

The verified registry versions are CLI `visonaut@0.5.4` and adapter `@visonaut/playwright@0.5.0` under `latest`. The approved Ariakit upgrade in [PR #7720](https://github.com/ariakit/ariakit/pull/7720) uses CLI `0.5.4` and adapter `0.5.0` with explicit public defaults. The consumer merged as [`643daf40`](https://github.com/ariakit/ariakit/commit/643daf405c84f5e8fc0db46dcf6b799c73116278) after complete native PR acceptance; ordinary main acceptance is also verified through native CI, signed Submit, the successful Visonaut check, authenticated service History, and a bounded service point read. The earlier verified CLI `0.5.3` and adapter `0.4.1` consumer belongs to the dated [PR #7718 adoption record](history/operations/adapter-comparison-defaults.md). The adapter has an exact Playwright `1.63.0` peer pin. The CLI is independent of that peer runtime. TanStack Start/Router and React remain the web framework. Keep the [package ownership map](../README.md#work-on-the-repository); D17 does not select a framework rewrite or package merge.

Trusted Submit verifies native Plan, the tested commit, source attempts, successful required jobs, artifact digests, and the complete capture inventory. The service accepts a run from the signed GitHub Actions identity alone: it compares no workflow Git blob and no adapter executor digest. Submit compares PNG captures against a service-pinned reference, using pixelmatch and the recorded consumer settings. The service validates signed provenance, reference binding, and receipt metrics before importing the result. For each uploaded image it checks the size and the SHA-256 digest; it does not decode the bytes. The Submit job decodes each capture when it compares. Upload, sealing, and a queued review receipt do not grant approval. See the [CLI](../packages/cli/README.md), [adapter](../packages/playwright/README.md), [receipt validator](../apps/web/src/api/local-comparison.ts), and [review guide](review-guide.md).

New storage uses one complete, immutable R2 inventory per run. D1 keeps run and snapshot pointers, changed capture and comparison rows, decisions, and image ownership pins. The first response of a run page has the changed, added, and removed captures from D1, with the review counts. Review reads the inventory to show the unchanged captures, one page of 2,000 at a time, when the reviewer opens them, searches, or follows a link to one of them. The first response also reads it for a closed run that is a summary, and for a run from before the service stored the baseline image with each changed capture. Accepted snapshots reuse the verified run inventory. Each inventory stores the current capture metadata and profile, the signed observed image digest, and the retained representative image. These identities can differ when comparison tolerances classify different bytes as unchanged. The inventory is flat, so reading a baseline does not follow older baseline chains.

A run has at most 11,000 captures. The service reads the complete capture list of a run and of its reference into memory for Submit validation and materialization, and a Worker isolate has at most 128 MB. The rule: two Submits at the same time in one isolate hold their capture lists in 64 MiB (67,108,864 bytes), about one half of that memory, and one Submit holds 2,913 bytes for each capture at the largest recorded point of the measurement, which gives 11,518 captures. The limit is the next smaller thousand. The [capture limit measurement](../apps/web/tooling/capture-limit/README.md) has the table, the model of a Submit that it measures, and the scope: local workerd, and not a hosted Worker. The limit can go when these steps work on one page at a time.

Existing deployments must use the [baseline cutover runbook](baseline-delta-cutover.md). The cutover preserves project configuration and the latest accepted baseline in a fresh database, and protects its images from old cleanup. Old history is not migrated. Keep the old database until a complete Submit, review, and main promotion pass against the replacement. This source change does not reset or deploy a database.
