# Ariakit release comparison for Visonaut decision O09

Checked on 2026-09-29. Local Ariakit checkout `fe73331c833108a7ce18e0df6ba04af9e83776b9`. This is read-only design evidence, not a proposed repository edit.

## Ariakit's actual path

- [`release.yml`](https://github.com/ariakit/ariakit/blob/fe73331c833108a7ce18e0df6ba04af9e83776b9/.github/workflows/release.yml#L1-L51) runs on every push to `main`. Its single `Version or publish` job has `id-token: write` and `contents: read`. It creates a GitHub App token for PR/commit access, checks out with credentials disabled, sets up dependencies, then invokes pinned `changesets/action@ae32849...` v2.1.2. The GitHub App token is distinct from npm OIDC identity.
- [Root scripts](https://github.com/ariakit/ariakit/blob/fe73331c833108a7ce18e0df6ba04af9e83776b9/package.json#L42-L45) are `version: changeset version && pnpm install --lockfile-only --ignore-scripts` and `publish: pnpm run build && changeset publish`. [Contributor instructions](https://github.com/ariakit/ariakit/blob/fe73331c833108a7ce18e0df6ba04af9e83776b9/CONTRIBUTING.md#L503-L514) say Changesets opens a `Publish` PR, and merging that PR automatically publishes affected packages. The workflow does not pack a checked tarball in an earlier job or use `--from-pack-dir`.
- The local workflow and setup action contain no `NPM_TOKEN`/`NODE_AUTH_TOKEN` publish secret and no `registry-url` configuration. npm's [trusted-publishing guide](https://docs.npmjs.com/trusted-publishers/) says GitHub Actions OIDC requires `id-token: write`, a matching npm package trusted-publisher configuration, and a compatible npm/Node version. That external npm configuration is not visible in the repository.

## What transfers to Visonaut

Visonaut's [current release workflow](https://github.com/ariakit/visonaut/blob/7e23173d11b1081f55021ef498e4c5c6d6a08131/.github/workflows/release.yml#L1-L60) is a manual `workflow_dispatch` on `main`; it has an `npm` environment, source-commit gate, same-run verified artifact, and selected package/tag controls. Its [release contract](https://github.com/ariakit/visonaut/blob/7e23173d11b1081f55021ef498e4c5c6d6a08131/.github/workflows/README.md#L50-L58) promises publication of exactly the verified tarball bytes. Copying Ariakit's `changeset publish` source path would retain OIDC/provenance and simplify custom publishing code, but explicitly retire that exact-archive promise. It need not copy Ariakit's automatic `main`-push cadence; O07 has already chosen Visonaut's manual trusted workflow.

Changesets v3 officially supports both [`changeset publish` from package source and `changeset pack --out-dir` with `publish --from-pack-dir`](https://changesets.dev/guide/cli). The [Changesets automation guide](https://changesets.dev/guide/automating) demonstrates separate pack and publish jobs for tighter OIDC permissions. OIDC provenance verifies the published archive's workflow/source identity; it does not choose between O09's source and exact-pack policies. The user's note says `I don't know`, so any settled O09 policy should reflect how the maintainer resolves the assurance/complexity tradeoff after reviewing both Ariakit and Clava.
